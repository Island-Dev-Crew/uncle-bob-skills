## Core mechanism

Mutation testing tests the tests. A tool makes many copies of the program, each with one small syntactic change (a **mutant**): flip `+`→`-`, `<`→`<=`, `==`→`!=`, negate conditionals, delete void calls, replace return values with defaults — the standard operator families PIT still ships today ([pitest](https://github.com/hcoles/pitest); [javapro.io guide](https://javapro.io/2026/01/21/test-your-tests-mutation-testing-in-java-with-pit/)). The full test suite runs against each mutant. A failing suite **kills** the mutant; a passing suite leaves a **surviving mutant** — proof that the change is unobserved by any assertion. **Mutation score** = killed/total. The fly in the ointment is the **equivalent mutant**: a mutant semantically identical to the original, which no test can kill; Budd & Angluin (1982) showed detecting equivalence is undecidable, and equivalent mutants run ~4–39% of mutants in practice ([JSERD](https://journals-sol.sbc.org.br/index.php/jserd/article/view/3588); [survey PDF](https://web.eecs.umich.edu/~weimerw/2022-481F/readings/mutation-testing.pdf)) — so a literal 100% score target needs an explicit equivalence-exclusion protocol.

## Provenance & history

The idea originates in Richard Lipton's 1971 CMU class paper "Fault Diagnosis of Computer Programs," and was made public by DeMillo, Lipton & Sayward, "Hints on Test Data Selection: Help for the Practicing Programmer," *IEEE Computer* 11(4), 1978 ([Jia & Harman survey](https://web.eecs.umich.edu/~weimerw/2022-481F/readings/mutation-testing.pdf); [SCIRP ref](https://www.scirp.org/reference/referencespapers?referenceid=953139)). Two hypotheses justify small mutations standing in for real bugs: the **competent programmer hypothesis** (real programs are close to correct, off by small syntactic slips) and the **coupling effect** (tests that catch all simple faults implicitly catch complex ones) ([UCL mutation repository](http://crestweb.cs.ucl.ac.uk/resources/mutation_testing_repository/theory.php)). Cost kept it academic for decades: mutants × suite-runtime is quadratic-ish in codebase size — Martin's own account of running it circa 2000 (four-minute suite × hundreds of mutants = overnight, unusable in a build) is in the interview transcript at `/private/tmp/claude-502/.../scratchpad/va-unclebob/transcript.txt`. Modern accelerations changed that: **incremental analysis** reusing prior results (PIT [issue #792](https://github.com/hcoles/pitest/issues/792); [StrykerJS incremental mode](https://stryker-mutator.io/docs/stryker-js/incremental/), 30min→<2min on typical PRs per [announcement](https://stryker-mutator.io/blog/announcing-incremental-mode/)); **coverage-targeted mutants** (only mutate covered lines); and **per-diff probabilistic mutation** — Google mutates only diff-touched, covered, non-"arid" lines, one mutant per line, at ~2B-LOC scale ([Petrović & Ivanković, ICSE-SEIP 2018](https://research.google.com/pubs/archive/46584.pdf); [TSE 2021](https://homes.cs.washington.edu/~rjust/publ/practical_mutation_testing_tse_2021.pdf)). Production tools: [PIT/pitest](https://github.com/hcoles/pitest) (JVM), [Stryker](https://github.com/stryker-mutator) (JS/TS via stryker-js, C#/.NET via stryker-net), [mutmut](https://github.com/boxed/mutmut) & [cosmic-ray](https://github.com/sixty-north/cosmic-ray) (Python), [cargo-mutants](https://github.com/sourcefrog/cargo-mutants) (Rust, zero-config), [gremlins](https://github.com/go-gremlins/gremlins) & [go-mutesting](https://github.com/avito-tech/go-mutesting) (Go).

## What holds up in 2026 for agent-directed engineering

Martin's move is real and public: he states he doesn't review agent code, instead measuring "test coverage, dependency structure, cyclomatic complexity, module sizes, mutation testing" ([his X post](https://x.com/unclebobmartin/status/2044114698451476492?lang=en); [O'Reilly live event](https://www.oreilly.com/live-events/ai-agents-for-clean-code-with-uncle-bob-martin/0642572376765/)). In the transcript he describes a specifier→coder→cleaner→**hardener**→QA pipeline where the hardener runs mutation testing "mercilessly" at 100% coverage, ~30 minutes instead of overnight (transcript, local path above). The economics inverted exactly along the axis that killed it in 2000: the loop is boring, mechanical, and verifier-checkable — ideal agent work — and the deterministic gate sidesteps the "guidelines, not rules" / lost-in-the-middle failure of prompt steering (transcript; UNVERIFIED as a general claim beyond his account). What a practical **per-story mutation gate** looks like, grounded in the Google/Stryker evidence: (1) scope mutants to the story diff, covered lines only; (2) run the language-native tool with incremental cache; (3) gate on **zero surviving non-equivalent mutants in the diff**, not a global score; (4) surviving mutants return to the coder agent as concrete kill-tasks ("write a test that fails on this exact change"); (5) an explicit equivalence ledger — a mutant may be excused only with a recorded justification, since 100% raw score is provably unreachable ([JSERD](https://journals-sol.sbc.org.br/index.php/jserd/article/view/3588)); (6) a runtime budget cap, because whole-module runs still take hours on big Go modules ([gremlins README](https://github.com/go-gremlins/gremlins)). This fits the repo's law: mutation testing converts "tests pass" (a claim) into "tests kill injected faults" (evidence from a check that could have failed).

## Skill seeds

- **mutation-gate** — per-story diff-scoped mutation run as a merge gate — encodes: zero surviving mutants on diff-touched covered lines, tool-emitted report hashed as the evidence artifact.
- **surviving-mutant-triage** — classify each survivor as missing-test / dead-code / equivalent — encodes: an equivalence ledger where every excusal carries a written justification; unexcused survivors block.
- **hardener-loop** — the merciless post-coder agent pass (CRAP + mutation) from Martin's pipeline — encodes: loop-until-green against deterministic tools, never prose rules; budget cap so the gate can't eat the productivity margin.
- **mutation-tool-select** — pick the native tool per language (pitest/Stryker/mutmut/cargo-mutants/gremlins) — encodes: incremental/diff mode required; whole-repo runs forbidden in the gate.
- **crap-threshold** — CRAP score (CC²×(1−cov)³+CC, Savoia & Evans 2007) ceiling per function — encodes: agent threshold (Martin uses 6 vs. human 4, per transcript) stated as enforced, with the score report as evidence.
- **coupling-audit** — periodic check that diff-scoped sampling isn't hiding whole-module rot — encodes: scheduled full mutation run with score trend, per Google's arid-line/sampling caveats.
